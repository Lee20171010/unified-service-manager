# Docker / OMV Compose deployment · 0.6.1

The release uses two images: `ghcr.io/lee20171010/unified-application:0.6.1` and `ghcr.io/lee20171010/unified-web:0.6.1`. Public images can be pulled without registry login. The current image platform is linux/amd64.

## OMV setup

In Services → Compose → Files, create `unified` or edit the existing project. Paste [compose.yaml](../deploy/omv/compose.yaml) into **File** and the following into **Environment**:

```dotenv
IMAGE_TAG=latest
ADMIN_TOKEN=replace-with-a-unique-random-token-of-at-least-32-characters
BIND_ADDRESS=127.0.0.1
PORT=4180
WEBDAV_URL=
WEBDAV_USER=
WEBDAV_PASSWORD=
```

Generate a token with `openssl rand -hex 32`, or retain the existing token when updating. Save and select **Pull**, then **Up**. The shipped configuration uses `IMAGE_TAG=latest` with `pull_policy: always`; Up also checks the registry. Set `IMAGE_TAG=0.6.1` to pin this release. No image build, tar download, manual mkdir/chown or separate initialization service is required.

Relative mounts resolve beside the Compose file. Select the desired data disk in OMV's Compose settings before initial deployment.

| Mount | Content |
|---|---|
| `./data:/data` | Database, inventory, jobs/logs, plugin imports/installations and archive cache |
| `./ssh:/run/ssh:ro` | Dedicated SSH keys and verified known_hosts |
| `./sources:/sources` | Application configuration snapshot sources and restore targets |
| `plugin-catalog:/plugin-catalog:ro` | Read-only compatibility source for legacy custom definitions; builtins use the image path |

The entrypoint prepares root-owned empty data/source directories and execs the server as 10001:10001 with no capabilities. Existing nonempty directories and other owners are preserved. SSH contents are never modified; keys must be readable by UID 10001, with suitably restricted permissions. With an explicit non-root Docker `user`, initialization is skipped and mounts must already be writable.

## Access

The Web service listens on NAS loopback port 4180. Use your HTTPS reverse proxy. If Tailscale runs on the NAS host, inspect `tailscale serve status`, then configure an unused HTTPS port, for example:

```bash
tailscale serve --bg --https=9443 http://127.0.0.1:4180
```

Use your own hostname and chosen port in both Web and Android, with the same administrator token. If Tailscale runs in a separate bridge container, configure its network path to Web instead of using the host's loopback address.

After connecting, install desired plugins and register your hosts/resources. The 11 available plugin definitions are not installed automatically. Register host addresses, SSH accounts and key file references; independently verify SSH host fingerprints.

## Updates and existing installations

Keep the same Compose project name, environment values and host mount paths. If existing data uses an absolute path, retain it instead of switching to an empty relative directory. With `IMAGE_TAG=latest`, use **Pull**, then **Up** to adopt the reviewed stable release. To select an exact release, change `IMAGE_TAG` to that numeric version first. With the CLI, use `docker compose pull` followed by `docker compose up -d`.

Application refreshes official GitHub metadata automatically at startup and every six hours. Both clients offer Check plugin updates and explicit Install/Update. Generic builtins update with the image. Existing installed plugins and custom definitions remain local under ./data/plugins. Keep the compatibility catalog volume and project identity during upgrade; modified legacy documents are copied into data without overwriting UI imports. No manual JSON download is needed for official online packages. See [PLUGIN-CATALOG.md](PLUGIN-CATALOG.md) for migration and offline behavior.

Earlier offline images remain usable under their existing tags. The first registry release contains security/privacy changes and must be pulled; changing an old tag does not apply those changes. Application 0.4.2 or newer initializes storage inside its entrypoint. Remove any earlier storage-init service/dependency and application cap_drop setting when adopting this Compose. An obsolete stopped storage-init container can be removed separately without deleting volumes.

Saved application data survives ordinary Up/Down and container recreation. Do not select volume deletion for routine updates. Manual edits outside mounted paths belong to the container layer and do not survive recreation. Changing the schema in future releases requires an explicit compatibility review; no new manager backup/migration feature is included in this release.

## Offline image bundle

The optional offline bundle generated by scripts/package-omv.sh pins its own numeric IMAGE_TAG and sets pull_policy: never. After docker load, use the bundled Compose/env and select Up without Pull. If using an online Compose file instead, the CLI equivalent is `docker compose up -d --pull never`. Restore pull_policy: always when switching back to registry updates.

## Release maintenance

Review every commit and image before publishing as described in SECURITY.md and AGENTS.md. Build/test from the reviewed commit; the manual publication workflow records image digests and links images to the source repository. Numeric release tags identify immutable contents. Both images pass the publication gates before their `latest` aliases move. Pull/Up is an administrator action; running containers do not update merely because an alias moved.

Local deployment tests use disposable directories and no remote hosts: `python3 scripts/test-entrypoint.py` and `python3 scripts/test-omv.py`. See [startup validation](VALIDATION-ENTRYPOINT.md) for the runtime contract.
