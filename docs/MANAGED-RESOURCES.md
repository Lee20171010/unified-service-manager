# 受管对象：服务、套件、应用插件与工具

状态：正式 0.3 backend／Web／Android 已接入受管对象、npm 操作与配置式宿主关联。当前支持范围见 [RUNTIME-0.3.md](RUNTIME-0.3.md)；以下保留完整产品设计。[预览入口](https://manager.example.com/next/)；运行边界沿用 [DESIGN-NEXT.md](DESIGN-NEXT.md)。

## 一、两层插件与一个总览

**Unified 管理插件**提供管理协议、配置字段和操作能力，必须在 Plugin 页面明确 Install。**远端软件／应用插件**是受管对象，登记在指定主机与账号的安装范围内。安装 Unified 的 bili 管理插件不会安装远端 billion-context；新增一个套件对象也只登记配置。远端安装需要另发起“安装套件”任务。

总览使用“受管对象”，按常驻服务、套件／CLI、应用插件、一次性工具过滤。操作由 capability 决定，不对所有对象强加 Start／Stop。npm 是安装来源，宿主插件是应用关系，常驻服务是运行能力：一个对象可以同时具备套件和宿主接入能力。

| 对象 | 当前 Mock 接入 | 操作 |
| --- | --- | --- |
| OpenCode、OpenChamber、Hermes、ChatGPT | 各自服务管理插件 | 状态、升级、启停、重启 |
| 一般 npm 包／CLI | npm 套件管理插件，填写包名 | 检查、安装、升级、卸载 |
| bili / billion-context | 专用套件管理插件 | 套件操作、诊断、关联 OpenCode／Hermes、接入／解除接入 |
| oc-codex-multi-auth | 专用应用插件管理 | 套件操作、诊断、关联 OpenCode、接入／解除接入 |
| halogen service 等自建对象 | 通用服务／工具插件 | 声明的生命周期或参数化工具动作 |

原来的备份应用和存储插件保持各自责任。插件 catalog 增加 `package-management` 分类，首批包规划为 `npm-packages/`、`billion-context/`、`oc-codex-multi-auth/`。这些是 Unified 管理插件目录，不是第三方 npm 包源码的副本。

## 二、配置与身份

套件实例记录 `host`、执行 `account`、Node 运行环境、安装 `scope`、实际范围目录、npm `packageName`、版本策略与管理插件 ID。范围有用户 prefix、项目目录、宿主管理的套件目录；Node/nvm 环境必须显式选择，不能使用中央进程的 HOME 或 PATH 猜测远端环境。

同一套件安装的身份由 **主机＋账号＋运行环境＋范围＋规范化目录＋包名**确定，禁止通过通用 npm 与专用接入重复登记同一安装。不同项目可独立管理同一个包。正式实现需在目标主机解析实际安装目录与管理器元数据；Mock 仅做路径规范化和确定性比较。

版本策略为指定精确版本或更新时解析 latest。提交任务时解析并固定本次版本，重连／排队不重新解析。Mock 的 `1.0.0-mock`、`2.0.0-mock` 只是版本变化样例，不代表上游真实发布版本。

## 三、宿主关系与状态

一份 billion-context 安装可关联同主机、同账号的多个相容应用。oc-codex-multi-auth 只提供 OpenCode 关系。关联记录只定义目标，不改宿主配置；用户另行点击“接入宿主”或“解除接入”，由专用插件建立任务。

每条关系分别记录宿主 ID、配置中是否已注册、实际载入版本、是否需要重启。套件升级只更新已安装版本，保留宿主已载入版本。明确重启宿主后再验证加载结果，不能仅凭文件安装成功声称运行中版本已更新。真实运行时无法探测时应显示“未知”，不能编造成功；Mock 用成功重启事件模拟观察值。

套件详情显示全部关联宿主；服务详情反向显示关联套件和加载状态。升级确认页列出影响对象，不自动重启宿主。解除接入后旧进程可能仍加载插件，保留加载状态并提示重启；所有注册和已加载引用解除后才允许卸载。

bili 的独立代理如果确实由管理员管理，可以另登记服务并关联套件；宿主自行维护的代理不自动变成一个可启停服务。第一版预览只提供套件与宿主接入流程。

## 四、任务、冲突与失败

所有安装、升级、卸载、接入、解除接入和诊断使用中央 Job 服务。包级任务锁定安装身份及关联宿主配置，避免更新与宿主重启／配置改动并行冲突；真正执行前再次验证能力和引用状态。

失败或中断不把已安装／已加载观察值改成成功结果。升级可使用现有 Shell／PTY Console，退出后保留独立排错 shell，任务终态及日志保持固定。手动 shell 操作后需重新检查受管对象状态，不能把命令输入本身当作成功证据。

卸载需要明确确认，保留管理记录和任务历史。停用／移除 Unified 管理插件只关闭管理能力，不卸载远端软件或删除其配置。敏感 OAuth 账号池和 token 不纳入本次 UI 管理，不回传到浏览器或 Android。

## 五、通用执行与专用接入

普通 npm 包使用通用管理插件；应用插件若有宿主配置、缓存或专用更新程序，则使用专用接入，不能默认执行 `npm install -g` 或 `npm update`。具体脚本仍需根据目标版本及安装方式验证。

本次设计参考已核对的上游资料：

- [billion-context README](https://github.com/ranxianglei/billion-context)：提供 npm／CLI 安装、原生宿主插件与代理运行方式，适合拆分套件安装和宿主关系。
- [oc-codex-multi-auth README](https://github.com/ndycode/oc-codex-multi-auth/blob/main/README.md)：包含宿主注册、独立 CLI 和专用更新流程；应由专用接入处理。

这些资料用于界定接入责任，不作为已经验证的真实安装脚本。本次没有安装、更新或读取用户现有 bili／认证插件设置。

## 六、交付与 API 方向

正式 API 增加受管对象 `kind`、配置 schema、capabilities、安装观察与宿主绑定。拟以 `/resources` 统一入口，现有 `/services` 在兼容期保持服务子集；旧客户端不得把未知类型当 Compose 执行。对象动作继续提交到中央 Job 服务，Web 与原生 Android 同步呈现所有能力。

Mock 沿用原先 `state.services` 数组保存受管记录，保留已有浏览器数据；UI 和规则已支持四类对象。这只是原型数据兼容策略，不等于正式数据库迁移。正式实现需明确数据库升级、资源 ID 兼容、安装范围检测、权限、套件版本解析、配置快照与回退。

验收：空插件启动；管理插件安装不动远端；登记对象不自动安装；一般 npm 包不需新写管理插件；重复安装身份被阻止；宿主关系独立；两应用共享套件时升级影响可见；载入版本直到逐个重启才更新；有关联时不能直接卸载；失败不伪造版本；两端操作与任务输出一致。
